# Pruebas de base de datos

`node --test supabase/tests/retail-database.test.mjs` crea una instancia PostgreSQL PGlite en memoria, configura una réplica mínima de Auth (solo ID, correo, confirmación y bloqueo), aplica las migraciones retail base y de seguridad diferida y ejecuta casos funcionales y adversariales. No conecta a Supabase ni modifica datos reales. Requiere dependencia de desarrollo exacta `@electric-sql/pglite` en el lockfile.

Comprueba permisos en las funciones y lectura, escritura directa denegada, exclusión de costos en caja, usuario sin membresía, membresía desactivada, propietario final protegido, validación numérica, duplicados, idempotencia, saldos obsoletos, recepción parcial, sobre-recepción, stock insuficiente, ventas/cotizaciones/conversión, reembolsos parciales con impuestos y descuento, cuarentena, entrega con fallo/reprogramación, promociones y conciliación contable.

`retail-smoke-rollback.sql` está preparado para revisión y ejecución en una base staging que ya tenga las migraciones y un propietario activo. Impersona su UUID únicamente dentro de una transacción usando el rol SQL `authenticated`, genera datos sintéticos, verifica operaciones y termina con `ROLLBACK`. No crea credenciales ni deja datos de prueba. Ejecutar con acceso administrativo a SQL es una prueba de funciones/permisos de datos, no reemplaza el login real con JWT ni la verificación de endpoints.

La prueba PGlite usa una conexión. **No demuestra concurrencia real, configuración de Auth de Supabase, publicación de Realtime ni APIs de producción.** Esos puntos requieren dos sesiones independientes y pruebas en el proyecto remoto antes de aprobar producción.

`node --test supabase/tests/legacy-import.test.mjs` prueba las migraciones base, seguridad, importación y ciclo documental con tablas originales y Storage simulados en PostgreSQL local. Verifica archivo/hash/mapas, rollback de datos y permisos, reejecución idempotente, identidades reutilizadas, pendientes/borradores, importes no recalculados, fechas dominicanas, costos históricos, cero garantía, imágenes lazy, aislamiento de archivo privado, eliminación de acceso API antiguo (incluidos permisos de columna) y rechazo de importes discordantes. No usa secretos ni datos reales en las fixtures.

Opcionalmente `RETAIL_LEGACY_PROFILE` puede apuntar a un archivo de perfil **sanitizado fuera del repositorio** con las colecciones `products`, `customers`, `suppliers`, `sales`, `purchase_orders`, `deliveries`; el tercer caso ensaya la transformación exacta de sus números y referencias en memoria. Reemplaza contactos por datos sintéticos e imágenes por un PNG de fixture; por eso no valida contenido multimedia real ni PII omitida. No guardar el perfil de negocio en el repositorio público. Sin esa variable, el caso se omite explícitamente.

`legacy-profile.sql` es un SELECT de diagnóstico sanitizado para revisar claves, tipos, identidades y cantidades antes de transformar. No devuelve notas, datos personales de contactos ni imágenes base64. La función privada `legacy_manifest()` usa los sobres completos en el servidor para verificar que el origen real no cambió entre revisión y corte.

La revisión final añade pruebas de categoría canónica y promoción por categoría, media protegida aun con una política Storage previa `USING(true)`, bucket preexistente público, base64/firma binaria falsa y privacidad del costo histórico para caja. Comprueba también que una devolución de venta importada conserva el costo de su snapshot y pondera el saldo actual con ese costo original.

`node --test supabase/tests/document-lifecycle.test.mjs` verifica edición/cancelación de cotizaciones, versiones obsoletas, reintentos, cálculo con catálogo, conservación de número/creación, precio pendiente, descuento autorizado de 100%, ausencia de documentos temporales, confirmación/cancelación de borradores sin replay de inventario, vinculación histórica estricta sin alterar snapshots/costos, cierre administrativo de venta antigua sin movimiento ni reembolso, permisos de roles, datos de auditoría protegidos y guardia de escritura previa al corte. También comprueba `search_path` vacío de las dos funciones opcionales de timestamps del sistema anterior.
